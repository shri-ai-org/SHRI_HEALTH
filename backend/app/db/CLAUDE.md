# backend/app/db/ — database layer (Anand)

Adopted from Sam's proposal (PR #9) per ADR-0011/D23, split into three PostgreSQL schemas in
one database: `clinical` (FHIR-shaped resources + `fhir_resource_history`), `admin` (normalized,
non-clinical tables), `audit` (`audit_event`, `break_glass_access` only).

## The `tenant_db` contract

Every endpoint uses `Depends(require("<permission>"))` and `Depends(tenant_db)` (Thulasi's
`backend/app/core/`). For the row-level security policies and triggers in this package to see
the right tenant, `tenant_db` must set exactly these three settings, transaction-local
(`set_config(name, value, true)`, not session-local — a pooled connection must never leak one
request's tenant into the next):

| Setting | Holds |
|---|---|
| `app.current_tenant_id` | the clinic, from the server-side session — **never** from a token claim or other client input |
| `app.current_user_id` | the signed-in user, for provenance and the audit chain |
| `app.correlation_id` | the request ID, carried into `audit_event.correlation_id` |

The implementation is the core's: `Database.tenant_session` in `backend/app/core/db.py` and
`tenant_db` in `backend/app/core/deps.py`. This package owns no engine and no session.
`app/db/session.py` only holds the hook that fills `tenant_id` on new rows from
`session.info["tenant_id"]`, which the core's `tenant_session()` sets to the clinic UUID (PR #28,
`app.core.db.TENANT_ID_INFO_KEY`). It fills only an empty `tenant_id` and never overwrites one.

## The /fhir session

`/fhir` does not use `tenant_db`. It runs as `shri_fhir_reader` (`FHIR_DATABASE_URL`, read-only,
D22/D23) with the clinic taken from the machine token. `backend/app/fhir/api.py` gets its
session from one dependency, `fhir_db`, a seam (like `machine_token_auth`) until Thulasi's core
provides it. The facade commits its own audit rows (`audit()`), including before a 404, so the
real `fhir_db` must set the three settings again on every new transaction, as `tenant_db` does.

`shri_fhir_reader` may also insert into `audit.audit_event` and nothing else on `audit` (no
SELECT, so the facade's audit insert never uses RETURNING; no access to `break_glass_access`).

Restricted charts are never served on `/fhir`, grant or not (D22; migration 0006). The database
does it: a RESTRICTIVE policy `fhir_hide_restricted`, for `shri_fhir_reader` only, on every
clinical table that can hold a chart's data (generated by `gen_db_rules.fhir_visibility_sql`).
A restricted patient is hidden, and so is every row below it: through the patient column, the
parent row(s), or the resource a history or provenance row is about. A new clinical table gets
a rule from the generator, or the generator stops and asks you to classify it
(`FHIR_PATIENTLESS`). When the facade cannot serve an ID it was asked for, it calls
`audit.record_fhir_lookup_denied(type, id)`, which returns nothing and writes the audit row
itself (restricted, or not-found), so the facade never learns which; the client gets the same
404 either way. `shri_app` is unaffected: in the API, break-glass decides (D37).

A role never bypasses RLS: `shri_app`, `shri_fhir_reader`, `shri_integration` and
`shri_reporting` are all `NOBYPASSRLS`. Only `shri_migrator` has elevated rights, and only for
schema changes, never for serving a request.

## The database roles (D23)

| Role | Use | Access |
|---|---|---|
| `shri_app` | the API | `clinical` + `admin` read/write per table (see `tools/gen_db_rules.py`'s classification); `audit.audit_event` select+insert, never update or delete (0004), `audit.break_glass_access` select+insert |
| `shri_fhir_reader` | `/fhir` (read-only, machine-token access) | `clinical` schema, `SELECT` only; `audit.audit_event` `INSERT` only (migration 0003) |
| `shri_integration` | the partner worker | narrow: order tables it reads to match a result, result tables it files into (select, insert, update; never delete; 0004), the three `integration_*` admin tables, and `audit.audit_event` `INSERT` only (0004) |
| `shri_reporting` | approved reports | nothing yet — no reporting views exist; grants come when they do |
| `shri_migrator` | migrations only | owns all three schemas |
| `shri_public` | the public pre-registration form (D96), the only write without a sign-in | `USAGE` on `admin` and `EXECUTE` on `admin.submit_pre_registration()`; no table privileges (0009) |

`shri_app`, `shri_integration` and `shri_fhir_reader` also have `USAGE` (never `CREATE`) on
schema `public`, where the rule functions that every trigger calls live (migration 0003). The
database image revokes all access to `public` from PUBLIC, so without it no write could fire
its triggers.

Role **creation** happens outside this package: locally/CI via
`infra/compose/postgres/initdb/10-service-roles.sh` (Thulasi); on RDS, by the master role plus
`shri_migrator` (ADR-0012). `sql/00_extensions.sql` here only creates the three schemas and
installs extensions, and grants to roles it assumes already exist — never create or `GRANT ...
TO` a role here without checking it isn't already owned by that script.

## Data-access helpers (for Vimal, Thulasi)

Writing a FHIR-shaped record correctly is easy to get wrong by hand: child tables, version
history, provenance, entered-in-error. Helpers take the `AsyncSession` that `tenant_db` gives
the endpoint, never a session of their own, so the clinic settings and the `require()` guard
always apply. Use these instead of touching the ORM models directly from another module's
`repository.py`:

```python
from app.fhir.serializer import to_fhir          # ORM row / history snapshot -> FHIR JSON
from app.db.constraints import patient_column      # which column says "this row's patient"
from app.db.errors import db_error_detail          # map a caught DBAPIError to (status, detail)
```

A full `fhir_store.create/update/entered_in_error/history` helper layer (as sketched in the
original Implementation Guide) is not built yet — this adoption PR is the schema and the
read-only `/fhir` facade only. Flag it if you need it before it exists.

## Conventions for the repositories (Vimal's review of #45)

How some contract shapes are stored. The property-to-column pairs a generator cannot infer are
in `docs/contract_mapping.yaml`, shown in the data dictionary's "Contract to column mapping".

- **Removing a diagnosis before signing (D24):** the Condition is the clinical record. It is set
  to `entered-in-error` with a reason and its Provenance, and is never deleted. The
  `encounter_diagnosis` row is only the link that ranks it on the encounter, a child row
  `shri_app` may delete, which frees its rank; the encounter's history snapshot keeps the old
  link. The database does not check "before signing" for link rows: the encounters service
  does. `UNIQUE (encounter_id, rank)` is not deferrable, so move ranks one at a time in an order
  that never collides: lowest first when closing the gap after a removal, highest first when
  making room for an insert.
- **A pending AI section:** stored with `entry_source` `clinician` and its `ai_suggestion_id`;
  the repository returns `ai-generated`. The database refuses `ai-generated` until the
  suggestion is accepted or edited (`shri_ai_provenance_guard`).
- **`PartialDate` (`YYYY`, `YYYY-MM`):** in the `*_period_start` / `*_period_end` columns,
  spanning the year or the month (`2019` is 2019-01-01 to 2019-12-31), so it stays queryable.
  The repository renders `YYYY` or `YYYY-MM` back when the period is exactly a year or a month.
  `*_string` is only for free text the clinician typed.
- **`gender`:** NOT NULL in the database, optional in the contract (D39, D44): the repository
  writes `unknown` when it is absent.
- **Eligibility:** the contract's `status` and `coverageStatus` are one column,
  `eligibility_check.status`: `complete` with `active` or `inactive` is `active` or `inactive`;
  `complete` with `unknown` is `not-found`; `error` with `errorCode: timeout` is `timeout`; any
  other `error` is `error`; `pending` is `pending`.
- **Check-in and its undo (D55, A42):** one live encounter per appointment (a partial unique
  index on `encounter.appointment_id`, ignoring `entered-in-error`), so check-in is idempotent.
  Undo sets the check-in encounter to `entered-in-error`, with its Provenance, and returns the
  appointment to `booked`; checking in again creates a new encounter.
- **`visitStatus` after an undo:** the latest `visit_flow_event` step of the appointment recorded
  after its last undo, the `recorded` time of the Provenance that set the check-in encounter to
  `entered-in-error`. With no step after it, the appointment is `booked` again and has no visit
  status. `visit_flow_event` stays insert-only: the steps before the undo stay as history.
- **Roles and permissions:** core's `ROLE_PERMISSIONS` (`backend/app/core/permissions.py`) is the
  only catalogue. `admin.role`, `admin.permission` and `admin.role_permission` are not seeded.
- **MRN (D41, migration 0007):** registration calls `SELECT system, value FROM admin.next_mrn()`
  in its own transaction and writes the patient's `identifier` row (type `MR`) with that system
  and value. The value is the prefix plus a six-digit number (`TEST-000123`). The counter row
  stays locked until the registration commits, and a rollback gives the number back. A practice
  without an `mrn_counter` row gets `P0001`; practice setup creates it. The number only grows,
  and the prefix and system are fixed once the first MRN is issued.
- **D39 coded demographics:** `patient.ext_{gender_identity,sexual_orientation,occupation,
  industry,tribal_affiliation}_{system,code,display,text}`, one contract `CodedValue` each. A code
  needs its system, a registered code system (`code_system.uri`); text alone is fine. They are
  not served on `/fhir` yet.
- **Employer (D38):** one `admin.employer` row per patient or related person. Clearing it
  (`employer: null`) deletes the row. Any change to it touches its patient or related person,
  so the ETag changes.
- **`selfPay` at check-in:** stored as `encounter.ext_self_pay`. The database refuses a claim
  for a self-pay visit, except a void (frequency `8`) of a claim sent before the visit became
  self-pay.
- **Practice settings (A49):** each is a `tenant_setting` row under a `setting_definition`
  key, which is lower case. The repository maps the contract's
  `showSexualOrientationAndGenderIdentity` to `registration.show_sogi_fields`, which defaults
  to `false`. `tenant_setting.version` is the row's `ETag` for `If-Match` on
  `PATCH /practice-settings`, bumped by the database on every update (as A41); the application
  never writes it.
- **An identifier's `documentId` (D56, migration 0008):** `identifier.supporting_document_id`,
  the scanned document (a `document_reference` filed with category `identity`). Only a
  patient's identifier has one, and only one of the same patient's documents.
- **Consent requirements (D59):** `admin.consent_requirement`, one row per kind and policy
  version. A new version is a new row (`422` when the kind already has it: unique
  `(tenant_id, kind, policy_version)`). The kind never changes; retiring sets `is_active`
  false; nothing is deleted. The contract's `required` and `active` are `is_required` and
  `is_active`; `version` is the ETag.
- **Payment receipts (D58):** `patient_payment.receipt_file_id`, the receipt PDF, a file in the
  same clinic, written in the payment transaction.
- **Pre-registration (D96, A51, migration 0009):** the public form calls
  `SELECT admin.submit_pre_registration(:practice_code, :idempotency_key, :request_hash,
  :details, :contact_consent, :source_ip, :user_agent, :request_id)` as `shri_public`, with no
  clinic set. `request_hash` is the SHA-256 (hex) of the body and `details` is the contract's
  `PreRegistrationDetails`. It returns nothing. `P0002` is an unknown or turned-off code (the
  `404`); `P0001` with constraint `idempotency_key_reused` is the `422`; the same key and body
  again is a success that stores nothing. The function writes the `anonymous` audit row, so
  core writes none for this route and skips its own idempotency store. The queue is
  `admin.pre_registration`, read and decided as `shri_app`: accept sets `status`, `decided_at`,
  `decided_by_user_id`, `patient_id` and `id_document_type` in one update (the identity
  check's who and when are the decision's); reject sets the reason code, with text for `other`.
  A decided request never changes. The contract's `submittedAt` is `created_at`; `deleteAfter`
  is 30 days after `created_at` while pending, or after `decided_at` once rejected, and absent
  once accepted. The practice's link is `tenant.pre_registration_code` and
  `pre_registration_enabled`.
- **Follow-up requests (D98, A52, migration 0010):** `clinical.encounter_follow_up`, one per
  visit, a child of the encounter: every change moves the encounter's version, so decline's
  `If-Match` is the encounter's ETag, and the encounter's history keeps each state. /fhir never
  serves it. The contract's `interval` is `interval_value` and `interval_unit`; `providerId` is
  `practitioner_id`; `requestedBy` is `requested_by_user_id`; `declinedReason` and
  `withdrawnReason` are both `status_reason`, by status. Booking sets `status` `booked` and
  `booked_appointment_id` in the appointment's transaction; cancelling the revisit sets `open`
  and clears it; rescheduling moves it to the new appointment. The request changes only while
  open, and a declined or withdrawn one is final (`shri_follow_up_guard`). Nothing is deleted.
  That only the requesting clinician withdraws is the service's check.
- **Portal sign-in (ADR-0013 §3 and §5, D92, migration 0011):**
  - **Before a clinic is known**, core calls three functions as `shri_app`:
    - `admin.lookup_portal_session(token_hash)` gives the session, clinic and patient of a
      live session of an active account;
    - `admin.lookup_portal_account(keycloak_user_id)` at `/callback` gives a pending-setup or
      active account;
    - `admin.redeem_portal_invitation(code_hmac, birth_date)` gives the clinic, patient and
      invitation, or nothing. Commit even when it returns nothing, so the failed try counts;
      the fifth revokes the invitation.
  - **Invitations:** the code is stored only as its HMAC, and a patient has at most one open
    invitation: revoke the old one before issuing a new one, in the same transaction.
  - **Accounts:** one per patient and Keycloak user.
    - `disabled` needs `disabled_at` and a reason.
    - `suspended` (a merged chart) needs `status_before_suspension` (pending-setup or active)
      and `suspended_by_merge_id`. The undo restores that status.
  - **Portal sessions** mirror `app_session`.
- **Staff back-channel logout (D94, migration 0011):** after validating the logout token, core
  calls `SELECT * FROM admin.end_backchannel_sessions(:jti, :jti_expires_at, :sid, :sub)` as
  `shri_app`, with no clinic set.
  - With a `sid`, it ends that Keycloak session; with only a `sub`, it ends every live session
    of that user.
  - It returns `(session_id, tenant_id, user_id)` for each session it ended, so core can write
    each session's audit row in its own clinic.
  - A reused `jti` raises `P0001` with constraint `logout_token_replayed`, and a token naming
    neither a session nor a user raises `22023`. Core answers 400 to both.
- **Merge undo (D51):** `undoAllowed` and `undoBlockedReason` come from
  `SELECT admin.patient_merge_undo_blocked_reason(:merge_id)`: `already-undone`,
  `records-changed`, or NULL when the merge can still be undone. The rule compares versions,
  so each service follows a fixed order in one transaction:
  - **merge:** lock both patients; insert `patient_merge` with both patients' current versions
    (`surviving_patient_version`, `merged_patient_version`) and one `patient_merge_record` per
    resource it will move, at its current version (`version_before_merge`); the database
    refuses a version that isn't current. Then move the records and add both patients' links,
    so every one of them moves by exactly one version;
  - **undo:** set `unmerged_at` (refused with `records-changed` when the rule says no), move
    the records back, then `SELECT admin.finish_patient_merge_undo(:merge_id)`. A record
    created or linked since the merge that points at a moved record (a new result on a moved
    visit) isn't seen by the rule; `finish` refuses that undo with `records-changed` instead
    of a key error. An undo that skips `finish` is refused at commit.

## Rules that never bend

- Every computed column is `STORED` (`persisted=True` on `Computed(...)`); a schema test
  (`tests/test_db_rules.py::test_no_virtual_generated_columns`) fails otherwise (D34 — PostgreSQL
  18 defaults to `VIRTUAL`, which cannot be indexed).
- IDs are UUIDv4 everywhere (D29) — `uuidv7()` is not adopted; it exposes creation time.
- Collation is C.UTF-8 in every environment (D33).
- No DELETE on resource tables; corrections use `entered-in-error`.
- Schema changes only through a new Alembic revision; never edit `sql_0001/`/`sql_0002/`.
- Regenerate `sql/*.sql` from the models (`python -m app.db.tools.gen_db_rules`) before writing
  a new migration's embedded SQL — never hand-edit the generated files.
