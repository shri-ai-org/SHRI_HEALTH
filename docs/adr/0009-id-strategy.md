## Context

## Decision

1. Every API resource ID is a UUID (RFC 9562), lowercase canonical form, generated by the server, opaque to clients.
2. **IDs are UUIDv4 everywhere** (D29), generated as Sam's schema does today: Python-side `uuid4` for primary keys, `gen_random_uuid()` for the audit `event_uuid`. Clients never infer time or order from IDs. ~~New IDs use UUIDv7 once the schema supports it; existing uuid4 values stay valid.~~
3. ~~**PROPOSED, pending Anand:** a record that exists in both stores has the **same UUID** in ours and in HAPI (client-assigned ID, `PUT <Type>/<uuid>`). HAPI-only records get a UUID generated by the FHIR client. Each HAPI resource also carries our identifier (`identifier.system` = our URI, `value` = UUID) for conditional operations if client-assigned IDs are not enabled.~~ Each record has one UUID in our one database (ADR-0011).
4. Business identifiers (MRN, NPI, member ID, claim number, license number) are properties, never IDs, and (except NPI) never in URLs.

## Alternatives considered

| Option | Why not |
|---|---|
| ~~HAPI server-assigned IDs plus a mapping table~~ | ~~Extra table and lookup on every call; retries before the mapping is saved create duplicates~~ |
| UUIDv7 (time-ordered) | Exposes each record's creation time to anyone who sees an ID in a URL or export, which is sensitive metadata in a medical system; the index cost of random UUIDv4 keys is negligible at clinic scale (D29) |
| Sequential integers | Reveal record counts and allow enumeration; collide across tenants |
| MRN as the patient ID | PHI in URLs (VD-G2); MRNs change on merge |

## Consequences

- ~~HAPI must allow client-assigned IDs for our resource types (HAPI configuration, Anand).~~
- Outbox retries are idempotent by construction (DATA_OWNERSHIP §3).
- One `Id` schema in `shared/common.yaml` for every ID.
